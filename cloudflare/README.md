# Hosted HealthSync API

`src/` implements the official hosted API at `https://api.healthysync.app`. It runs as a Cloudflare Worker backed by D1, with separate upload and read-only agent tokens per workspace. The [upload contract](../backend/UPLOAD_API.md) is shared with the [self-hosted FastAPI backend](../backend/README.md), which is a separate deployment.

## Development

Run from the repository root with Node.js 22.12 or later. The Worker uses the pinned Wrangler and TypeScript dependencies in `web/`.

```bash
npm ci --prefix web
npm --prefix cloudflare run typecheck
npm --prefix cloudflare test
npm --prefix cloudflare run dry-run
```

The tests use local data and cover the Worker, summary cache, and legacy Supabase forwarding function. See the [hosted operations runbook](../docs/operations/cloudflare-hosted.md) for deployment and recovery, and the [legacy migration guide](https://healthysync.app/docs/agent-access#cloudflare-migration) for agents still configured with the old URL.

## Hosted admission and deletion behavior

- The [Workers rate-limit bindings](https://developers.cloudflare.com/workers/runtime-apis/bindings/rate-limit/) admit workspace provisioning by Cloudflare's `CF-Connecting-IP` (10 requests per 60 seconds) and protected routes by the HMAC of the bearer (300 per 60 seconds across routes). They run before body parsing or D1 auth and return `429` with `Retry-After`. Counters are approximate and per Cloudflare location; the D1 storage bound is separate. The Supabase bridge keeps the bearer and upstream status/headers. It does not supply a trusted original IP: bridged anonymous requests can share an egress-IP bucket. Do not key by `X-Forwarded-For` or another caller-controlled header.
- A D1 trigger ledger limits each workspace to **512 MiB of net logical ingest growth** from migration `0006`. It charges fixed per-row weights for health rows, batches, device associations and deletion records, plus stored UTF-8 metadata bytes. There is no legacy count or backfill to run: existing history is grandfathered, and deletes credit the same weights. Rewriting a row without growing its metadata does not recharge the row. Exhausting the budget aborts the upload with `507`, including any deletes, batch changes or tombstones in the same transaction; an existing row can normally be deleted to free space, but a new export or tombstone also needs room. This is not a measurement of D1 file size or a database-wide cap. Use approved capacity or retention changes, not a ledger reset, to relieve exhaustion.
- `health-data` allows up to **300,000 candidate metric/workout rows** per uncached summary, including rows excluded by `end_at`. On overflow it returns `503` without partial summaries; callers can narrow dates or types or use the paged record endpoints. An aggregate is preferred only with a `healthkit:aggregate:<matching-type>:<valid-day>` ID, `daily_sum` or `daily_average` in `aggregation`, and `aggregation_period=day`. This recognizes the app's format, not a trusted attestation from HealthKit. Raw UUIDs always remain ordinary samples. Date grouping still uses the export timezone, not the date encoded in the ID.
- D1 commits a deletion and its durable tombstone in the same authorization-guarded batch as record writes. The scope is workspace, device, kind and ID. HealthKit UUIDs are not reused, so a deletion for `healthkit:<UUID>` wins permanently, regardless of device clock, retry time or a later-generated backfill. Reusable IDs allow a correction with `generated_at` strictly newer than their deletion; a stale delete cannot erase a newer row. At equal timestamps a delete wins, except for a deliberate delete-and-replace in the same export with no competing delete. Retries must keep their export ID and original `generated_at`; a reused export ID with a changed timestamp returns `409`. This ordering for reusable IDs assumes a consistently ordered device clock. Backwards clock jumps can make updates look stale after a delete, and received time cannot establish freshness. Deletes accepted before migration cannot be reconstructed from the hosted rows. Retain tombstones for the workspace lifetime; reset removes the whole workspace and its tombstones.

## Production reconciliation gate — do not deploy this checkout

Cloudflare metadata on November 18 showed the active Worker at version `338702b7-a024-4381-86ee-e662fa75da5f`, with `PROVISION_LIMITER` (`47001`), `TOKEN_LIMITER` (`47002`), Analytics Engine `USAGE` (`healthsync_usage`), and app-version/paywall bindings. The active bundle also has billing code not present here. No current upstream branch or reachable Worker history contained those production additions. `origin/codex/healthysync-app-cloudflare` (`e0155a0`) is an older tracked snapshot, not a production baseline. Recover the canonical release source and original bindings from the release owner, reconcile against the active version, and apply these changes there without dropping billing, entitlement, version-gate, or usage-accounting behavior. Verify the exact deployed limiter key/route logic and legacy traffic before changing the release.

Production already has `0001_hosted.sql` through `0004_summary_revisions.sql`, then **`0005_paywall.sql`** and an `entitlements` table. Keep slot `0005` for the original billing migration; don't invent it, reuse its slot, or recreate entitlement data. Verify the migration names and definitions, and rehearse the order on an isolated copy with the recovered release: summary revisions → paywall → `0006_ingest_safety.sql`. Fresh checkouts apply tracked migrations in filename order with an intentional gap; they are not complete billing environments. Lock writes before the reviewed `0006` migration and do not unlock until the reconciled Worker is active. Count deletions from `DELETE … RETURNING`, not D1's `meta.changes` (it includes ledger trigger updates). A rollback that re-enables old writers would bypass tombstones; plan a lock or a forward fix that retains the new data and tombstones.

**The thresholds are not validated for production.** Use the reconciled accounting and private staging telemetry to size both limits before release: measure peak per-workspace growth/headroom, large backfills and deletion-only batches, live database file/page headroom across all workspaces, D1 rows read/written and latency with the ledger, summary request candidate counts/CPU/cache misses including the largest histories, and direct vs. bridged admission. Verify migrated data and billing compatibility on an isolated restore; do not run a migration or submit health or billing data from this checkout.
